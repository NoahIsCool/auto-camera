# ac-vision

Detection and per-frame tracking for Auto Camera, behind traits that do not
depend on a model runtime.

| Item | What it does |
|---|---|
| `Detector` | Slow, open-vocabulary detection: `detect(&mut self, &VideoFrame, &[PromptQuery]) -> Result<Vec<Detection>, VisionError>` |
| `Tracker` | Fast per-frame tracking of known subjects: `start`, `update`, `stop`, `tracked` |
| `TemplateTracker` | Pure-Rust NCC template tracker (grayscale pyramid, constant-velocity prediction, local search, 0.95/1.0/1.05 scale search, ambiguity check) |
| `ScriptedDetector` | Detections from a closure or keyframe table, for tests and demos |
| `OnnxOwlDetector` | OWLv2 / OWL-ViT on ONNX Runtime, feature `onnx` (off by default) |
| `owl::*` | Pure OWL pre/post-processing: letterbox, CLIP normalization, sigmoid, box decoding, token packing |
| `matching::*` | People-first prompt matching: parse a prompt's object, pick the people holding it |
| `boxes::*` | `clamp_box`, `cxcywh_to_rect`, `nms_indices`, class-aware `nms` |

All boxes are normalized source coordinates (`ac_core::Rect`), clipped to the
frame; scores and confidences are in `0..=1`.

## Template tracker

See the `tracker` module docs for the algorithm, trust rules and cost model.
In short: frames are reduced to a 384 px wide luma pyramid; each subject is
matched on the level where its box is at most 32 px, over a window of half its
size around the constant-velocity prediction. It moves only on a strong,
unambiguous peak; otherwise it coasts and reports low confidence. The
detector re-anchors subjects; the tracker never retires one by itself.

Measured with `cargo run --release -p ac-vision --example track_bench` on a
4-core 2.1 GHz Xeon VM: 16 subjects on 1080p in 7.4 ms per frame (most of it
the RGBA-to-luma downscale, which is shared by all subjects).

## OWLv2 through ONNX Runtime (`--features onnx`)

**Status:** both export layouts below were run on an M3 Max (macOS 27,
2026-10-15) with `google/owlv2-base-patch16-ensemble`, torch 2.14,
transformers 4.57 and ONNX Runtime 1.31; the tensor names and shapes match
the table. On real frames the Rust detector returns the same boxes as the
Hugging Face reference (`Owlv2Processor` + `Owlv2ForObjectDetection`), with
scores within about 0.05 (the resampling filters differ). The tests use
synthetic graphs with the same interface (`tests/fixtures/owl`, generated by
`make_fixtures.py`), so no test needs the real weights.

Measured on 1280×720 frames, split export, two prompts:

| Provider | Load | First call | Steady state |
|---|---|---|---|
| CoreML (MLProgram, static shapes) | 140–176 s cold, 26–29 s from cache | 0.3 s | 185 ms |
| CPU | 0.4 s | 2.0 s | 2.0 s |

### Building

The `ort` crate (2.0.0-rc.13) downloads ONNX Runtime 1.28 at build time. On
Apple Silicon the download includes the CoreML execution provider, which the
detector registers when `OwlConfig::use_coreml` is set (the default); nodes
CoreML cannot run fall back to the CPU. Only nodes with static input shapes
go to CoreML: given the dynamic query axis, MPSGraph aborts the process while
compiling the text encoder. The first load compiles the graphs for CoreML,
which takes two to three minutes and about 7 GB of memory. Two caches keep
later loads short (26–29 s): ONNX Runtime's, in `coreml-cache/` next to each
graph (about 1.6 GB for OWLv2 base, reused until the graph file changes),
and CoreML's own, which macOS keeps per executable in
`~/Library/Caches/<executable name>/com.apple.e5rt.e5bundlecache`. The second
is written only when a compile finishes, so the first run of a new
executable (`auto-camera`, or the `owl_detect` example) must stay up until
detections start. The engine loads the detector on its discovery thread, so
the window and program run while it compiles; discovery requests time out
until it is ready. To build against a local ONNX Runtime
(1.27 or newer) instead, for example the `libonnxruntime` inside the
`onnxruntime` Python wheel:

```sh
export ORT_LIB_LOCATION=/path/to/dir/with/libonnxruntime   # .so or .dylib
export ORT_PREFER_DYNAMIC_LINK=1
export LD_LIBRARY_PATH=$ORT_LIB_LOCATION                    # DYLD_LIBRARY_PATH on macOS
cargo test -p ac-vision --features onnx
```

### Getting a model

Two layouts are accepted (`OwlModel`):

Both exports need Python 3.10 or newer; keep the environment and the
Hugging Face cache under the gitignored `models/`:

```sh
python3 -m venv models/.venv && source models/.venv/bin/activate
export HF_HOME=$PWD/models/hf   # about 600 MB of weights per download
```

The export reports small differences from the reference model (logits about
0.002, boxes about 3e-5); those are float rounding, not a broken export.

**Combined** (simplest; the text tower runs on every call):

```sh
pip install optimum-onnx pillow   # older releases: pip install "optimum[exporters]" pillow
optimum-cli export onnx --model google/owlv2-base-patch16-ensemble \
    --task zero-shot-object-detection models/owlv2-base-onnx/
# -> models/owlv2-base-onnx/model.onnx and models/owlv2-base-onnx/tokenizer.json
```

```rust
let detector = OnnxOwlDetector::load(
    OwlModel::Combined { model: "models/owlv2-base-onnx/model.onnx".into() },
    Path::new("models/owlv2-base-onnx/tokenizer.json"),
    OwlConfig::default(),
)?;
```

**Split** (text embeddings cached per prompt, so steady-state detection runs
only the image side; the faster choice):

```sh
pip install torch transformers onnx onnxruntime pillow
python crates/ac-vision/scripts/export_owlv2_split.py \
    google/owlv2-base-patch16-ensemble models/owlv2-split-onnx/
# -> text_encoder.onnx, detector.onnx, tokenizer.json; prints a parity check
```

In a studio config the split layout is `model = ".../detector.onnx"` plus
`text_encoder = ".../text_encoder.onnx"`.

### Checking an export

The `owl_detect` example loads an export the way the engine does, runs it on
raw RGBA frames and prints every detection and the time per call:

```sh
ffmpeg -ss 10 -i talk.mp4 -vf fps=1,scale=1280:720 -frames:v 4 \
    -f rawvideo -pix_fmt rgba frames.rgba
cargo run --release -p ac-vision --features onnx --example owl_detect -- \
    models/owlv2-split-onnx 1280 720 frames.rgba "a person" "a guitarist"
```

`AC_OWL_CPU=1` skips CoreML; `AC_OWL_THRESHOLD` sets the score threshold.

### Prompts: people first

OWLv2 boxes the thing a prompt names: "a person playing guitar" boxes guitars
(also guitars on stands and in photos on a projection screen), "a person
speaking at a lectern" boxes lecterns, tables and microphone stands. So the
detector does not return a prompt's own boxes. By default
(`OwlConfig::people_first`, `people_first` in a studio's `[detector]`) every
pass also asks for "a person" and for the object each prompt names, and a
prompt picks the people whose box holds its object; the detections are whole
people. "a person playing guitar" asks for "a guitar", "a man in a red shirt"
for "a red shirt". A prompt with no person word ("a guitarist") attaches its
own boxes like an object. A prompt that only describes a person ("a woman", "a
person speaking", "a tall person"), or whose object is another person ("a man
next to a woman"), also attaches its own boxes, so it never picks the other
person. "a person" or "people" picks everyone. See the `matching` module for
the rules and their tests.

Thresholds come on two scales. OWLv2 scores a named object high and any
description of a person low, however well it fits. So objects need
`score_threshold` (0.3 by default: real guitars score 0.6 to 0.75, nothing
else above 0.26), while everyone and described-person prompts need
`person_threshold` (0.15), unless a query sets its own threshold; people
themselves always need an "a person" score of `person_threshold`. A studio's
subject store would otherwise drop those low person scores, so when
`[subjects] min_score` is not set, its floor follows `person_threshold`.

An object is a person's when at least 45% of the smaller of the two boxes
lies inside the other: a guitar mostly inside its player, or a drummer mostly
inside a drum kit larger than they are. For objects smaller than the person,
as guitars are, that is the object's own box, so the numbers below are
unchanged by it. A "person" box holding two or more other people is a group
and is dropped. The extra queries cost nothing measurable: 183–185 ms per pass on
CoreML for 2, 3, 5 or 9 queries.

How the strategies compared, on 20 frames each of a band (three guitarists,
a singer, a drummer, a keyboard player) and a sermon rehearsal (one speaker
walking the stage, guitars on stands), with the speaker and every guitarist
hand-checked; a chosen person is a hit when its box has IoU ≥ 0.5 with a
labelled one (Python reference on CPU, best thresholds for each):

| Strategy | Guitarists found (of 60) | False subjects | Speaker found (of 20) |
|---|---|---|---|
| The prompt's own boxes (before) | boxes on guitars, not people | many | 0 |
| Prompt score on each person's own box | 58 | 65 | 0 |
| Prompt's own boxes attached to people | 58 | 9 | 0 |
| Object ("a guitar") attached to people | 60 | 2 | 1 |
| Object attached, with 60% of it inside instead of 45% | 45 | 22 | not measured |
| Both attached | 60 | 2 | 1 |
| Object attached, in Rust on CoreML, with the group rule | 59 | 2 | 1 |

The two remaining false subjects are the speaker walking right in front of a
guitar on a stand. The speaker is found once: OWLv2 sees objects, not
actions, and this speaker never stands at the lectern. "Speaking", "singing" and
"holding a microphone" (the band's guitarists sing into stand microphones)
cannot be told apart from boxes; that would take an action- or audio-aware
model. Prompts work best when they name something visible on the person.

### Expected tensors

| Graph | Name | Type and shape |
|---|---|---|
| combined, text encoder | `input_ids` | `i64 [Q, 16]`, CLIP ids `[BOS, …, EOS]`, padded with `!` (id 0) |
| combined, text encoder | `attention_mask` | `i64 [Q, 16]` |
| combined, detector | `pixel_values` | `f32 [1, 3, S, S]`, S = 960 (base) or 1008 (large) |
| detector | `query_embeds` | `f32 [1, Q, 512]` |
| text encoder | `text_embeds` | `f32 [Q, 512]` |
| combined, detector | `logits` | `f32 [1, P, Q]`, P = (S/16)² = 3600 for base |
| combined, detector | `pred_boxes` | `f32 [1, P, 4]`, `(cx, cy, w, h)` in `0..1` of the padded square |

Names can be changed through `OwlConfig::names` if an export differs; loading
fails with the graph's actual input names when one is missing.

Preprocessing follows the OWLv2 processor: the frame is placed at the top-left
of a square and padded with grey (0.5) at the bottom/right, resized to S
(anti-aliased), and normalized with the CLIP mean and standard deviation.
Postprocessing applies a sigmoid per (patch, query), keeps scores at or above
the query's threshold (`OwlConfig::score_threshold`, default 0.3, or
`query_thresholds`; with `people_first`, see the thresholds above), maps boxes back to the source by undoing the padding,
clips them, and runs class-aware NMS (IoU 0.3, at most 16 per query). OWL-ViT
v1 exports (`google/owlvit-base-patch32`, S = 768, P = 576) use the same
graph interface; v1 was trained on stretched rather than padded images, so
expect slightly lower scores.
